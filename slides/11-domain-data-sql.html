Real-World Case Study

Domain Example 3: Data Engineering & SQL

Scenario: Optimizing a slow customer retention query with SQL window functions.

❌ Low-ROI Brute Force Prompt Tokens: ~160k (Dumps all models)

"My customer retention SQL query is super slow and timing out. Here are all our analytical models @models. Rewrite it to be fast."

Why this fails:
  • Dumps entire database directory, burning 160,000 tokens on schema noise.
  • AI cannot see table volume or indexes; suggests generic non-applicable optimizations.
  • Creates hallucinated temporary tables.
✅ Value-Maxed Precision Prompt Tokens: ~1.8k | Latency: 1.0s 
Context: `@monthly_retention.sql`

Problem: Slow correlated subquery calculating each user's latest order date causes full table scans.

Task:
1. Replace the correlated subquery with an efficient window function:
   `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY order_date DESC) AS rn`.
2. Filter for `rn = 1` and flag `is_churned = true` where `order_date < CURRENT_DATE - INTERVAL '90 days'`.

Constraints:
- Standard ANSI SQL / PostgreSQL syntax.
- Maintain existing output column contracts: `(user_id, last_order_date, is_churned)`.
Why this wins:
  • Specifies the exact algorithmic fix (Window Function over Subquery).
  • Instant 1-second generation without loading massive database schemas.

🎙️ Speaker Talking Points (4 mins):

  • The Data Trap: Dumping 15 SQL models into Cursor chat forces the model to read thousands of lines of unrelated schema DDL.
  • Identify the Bottleneck: Instead of asking "make my query fast", tell the model the specific bottleneck (e.g. "correlated subquery causing table scans, replace with ROW_NUMBER() window function").
  • Constraint Power: Stating the exact target dialect (e.g. PostgreSQL vs Snowflake vs BigQuery) avoids dialect-specific syntax errors.
